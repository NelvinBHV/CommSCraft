Scope: PR #35, source-only/offline behavior. This report does not attest to Microsoft Windows Full Client interoperability or successful authenticated sign-in.

## DNS/SRV

* **RFC 2782 (February 2000), §3** — Process SRV records in ascending numeric priority groups, use weighted selection within a group, and treat a single-dot target as absence of service. Source: `crates/commscraft-core/src/discovery.rs`, `order_srv` and `SrvRecord::new`. Fixtures: `weight_and_priority_follow_rfc2782`, `srvs_with_equal_priority_never_precede_a_lower_priority_group` and `dot_target_is_not_a_connectable_endpoint`. Negative defensive fixture: `invalid_rng_draw_fails_closed_without_modulo_bias_or_panic` (invalid RNG contract is an application-specific fail-closed choice, **not** an RFC requirement). URL: https://www.rfc-editor.org/rfc/rfc2782#section-3 .
* **MS-CONMGMT §3.1.5** — Four published Microsoft SRV query names and precedence are represented by `Service::ALL` and `tls_candidates`. Source fixture: `microsoft_names_cover_four_srv_services`; transport-security fixture: `never_includes_plaintext_dns_candidates`. Microsoft clause: https://learn.microsoft.com/en-us/openspecs/office_protocols/ms-conmgmt/40d79c10-2275-4e52-bb4b-67c703d092c3 . **Partial only**: actual parallel DNS queries, DHCP option 120 discovery, reachability, and TCP group processing are not implemented; TLS-only intentionally omits insecure transports. Version-specific document revision comparison remains pending.

## Bounded DNS answer expansion — subsequent phase (2026-10-18)

A source review identified that `order_srv()` bounds **each** answer vector to 256, but `tls_candidates()` previously accepted any number of separately supplied service-answer batches and appended unbounded distinct endpoint candidates. The aggregate endpoint set is now limited to **256** through `MAX_TLS_CANDIDATES` in `discovery.rs`, without enabling plaintext service records. Tests: `hostile_many_duplicate_service_answers_have_bounded_candidate_output` (adversarial multi-batch input) and `empty_dns_answers_keep_tls_only_fallback_and_unique_hosts` (fallback recovery). Audit linkage: `RFC2782-BOUNDED-OFFLINE-ANSWER` in `release/dns-register-clause-fixtures.json`. This bound is **project security policy**, not an RFC 2782-required value; [RFC 2782 §3](https://www.rfc-editor.org/rfc/rfc2782#section-3) defines priority/weighted SRV selection. [MS-CONMGMT §3.1.5](https://learn.microsoft.com/en-us/openspecs/office_protocols/ms-conmgmt/40d79c10-2275-4e52-bb4b-67c703d092c3) is contextual to discovery; full DNS I/O and actual Microsoft service sequencing remain unimplemented. REGISTER RFC 3261 §10.2 and the existing 423/timeout tests remain in place, with no additional credential or server registration functionality introduced in this commit. No new full-feature normative certification or live interoperability is asserted. CI results for final HEAD must be checked separately.

## REGISTER direct-response bounding — 2026-10-18

The offline response observer can accept caller-constructed `SipMessage` values without passing through the bounded wire parser. `matching_binding` now rejects more than 128 headers or any response header value over 16 KiB before scanning the Contact binding. Negative fixtures `oversized_direct_response_headers_are_rejected_without_acceptance` and `oversized_contact_header_is_rejected_without_acceptance` ensure the final response is rejected rather than accepted. Boundary/recovery fixture `auth_retry_cseq_boundary_rejects_out_of_range_new_transaction` checks that a 401-challenged transaction with CSeq `u32::MAX` does not wrap when planning a fresh REGISTER. RFC 3261 (June 2002) §§10.2.1, 10.2.2 and 20 define request sequencing/header handling: https://www.rfc-editor.org/rfc/rfc3261#section-10.2 . The 128-header and 16-KiB limits are **project hardening**, not mandatory RFC constants. Microsoft MS-SIPREGE §4.1.1 registration example is context rather than claimed full compatibility: https://learn.microsoft.com/en-us/openspecs/office_protocols/ms-siprege/bc4b0245-339d-490c-ba67-2410e1513ed9 . The proposed evidence checks local fail-closed processing, not real authenticated registration. CI for the final HEAD must pass before completion is claimed.

CI correction: the initial boundary fixture incorrectly used CSeq `u32::MAX` as a valid request; the existing SIP transaction parser correctly rejects anything above 2147483647. The replacement fixture uses 2147483647 as its valid initial CSeq and expects the proposed next transaction (2147483648) to be rejected (`RegistrationError::Transaction`). Historical failing runs are retained. Confirmation of the new exact HEAD awaits GitHub Actions.

## REGISTER Contact URI syntax hardening — 2026-10-18

An offline `200 REGISTER` reply can supply a `+sip.instance` matching the local device while supplying an empty, non-SIP, or nested-angle Contact URI. The observer now rejects these URI forms **before** associating a binding with that local instance. Positive fixture: `valid_contact_uri_can_report_unverified_binding`; negative fixture: `malformed_contact_uri_cannot_claim_our_instance` (`crates/commscraft-core/src/registration.rs`). The new linkage row `RFC3261-CONTACT-URI-GUARD` in `release/dns-register-clause-fixtures.json` refers to RFC 3261 (June 2002) §20.10, https://www.rfc-editor.org/rfc/rfc3261#section-20.10 . Microsoft MS-SIPREGE §4.1.1 provides contextual response examples, https://learn.microsoft.com/en-us/openspecs/office_protocols/ms-siprege/bc4b0245-339d-490c-ba67-2410e1513ed9 . This conservative URI gate does **not** implement full RFC 3261 URI equivalence, authenticate replies, or certify Microsoft interoperability. `scripts/test_dns_register_clause_fixtures.py` now expects five source-fixture records. DNS/SRV priority and bounded TLS-only selection remain covered by prior fixtures; no DNS networking is added. Final exact-SHA GitHub Actions and historical failures are evaluated separately. `main` and release gates are untouched.
